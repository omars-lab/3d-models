An approval to print covers one send of one plate. Omar ticks the Approve box on `docs/design/plates/<name>.md`, or says yes in chat naming the plate. Either way the session records it with `python3 .claude/skills/manage-approvals/scripts/plate_approve.py <page> --approved --by "<who, how>"`, which writes a dated row (`| Date | Decision | By | Covers | Spent by |`) in the page's `## Approvals` table and unticks the box. Approval is never in frontmatter (D-096, Omar 2026-10-03: "approval shouldnt be in frontmatter, we should have astandardized apprval table", "since we might do multiple approvals on same design"; he picked "Tick, table records"). The send spends the row: `Spent by` becomes `sent <date>`, and a `sent` timeline row is added. A Bambu Studio send is recorded with `--sent --via "Bambu Studio"`. A reprint needs a new yes.

**Why:** Omar, 2026-10-03: "i dont want to blindly print the experiment that showed us the plate was setup wrong", and "we should have timelog of all the approved re-prints against a plate". A tick left after a Bambu Studio send (sheets-04) looks exactly like a fresh one, so only a recorded open row counts.

**How to apply:** never send on an earlier "go ahead" or an old tick; `plate_approve.py <page> --status` answers, and `bambu print send` asks the same tool (`tools/bambu/src/send-gate.ts`), so a refusal there is the answer, not something to route around. A recipe change resets the yes (D-097, Omar's answer to call 6: "changes to a file should reaet yes - but indont want a file for every iteration"): the recipe changes in place, each content change is a numbered iteration in `.claude/skills/manage-approvals/approvals.yaml` and `iteration: N` on the page, a yes covers `iteration N @ <10-hex origin/master commit>` (a branch commit is refused: squash merges drop them), and hook 39 (P9) refuses an unrecorded change until `plate_approve.py <plate> --iterate` records it and marks the open yes `reset <date>`. The hook never edits or stages itself (shared checkouts). A comment-only edit is not a change. Only the recipe file is hashed: a bikar `.bkr` change makes no iteration. Production plates (D-095, "yes prod plates get standing approval, treat all current plates as experimental"): a standing approval, held only while the prints still show production and the recipe matches the pinned `recipe_hash`; promotion writes a `standing` row (`plate_approve.py --standing`). A production recipe never changes in place: "recipe change should be in a new experimental plate derived from a prod plate" → `plate_grade.py --derive`.
