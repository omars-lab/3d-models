- bikar uses a dotenvx sidecar (`.env.encrypted` committed, `env-*` Makefile targets, pre-commit plaintext/keyfile gate, `manage-secrets` skill). The key is backed up as LastPass entry `dotenvx/bikar`; `env-keys.sh` derives the entry name from the **origin remote**, so pushing from a worktree cannot mint a second entry, and `make env-status` syncs before comparing because a push followed by a cache read once falsely said "NOT backed up" (inviting a redundant push, the one op that overwrites the vault).
- **The same sidecar machinery was ported to the blog `omars-lab.github.io` (PR #226, 2026-09-14, LastPass entry `dotenvx/omars-lab.github.io`).** The port surfaced TWO latent bugs bikar's version still has: (1) **dotenvx overlays `process.env` on BOTH encrypt and decrypt** — a colliding exported shell var (a bare `STUDIO_HOST=studio`) silently substitutes its value, giving phantom drift in `check` and a WRONG value written by `bootstrap` on the next machine. Fix: run every dotenvx call via a `dotenvx_isolated` helper that `env -u`'s the file's own key names (names are plaintext even in the sidecar). (2) **dotenvx does not encrypt comment lines** — a commented-out `# CF_API_TOKEN=…` rides into the committed sidecar as plaintext; gitleaks catches it, the comment-skipping `check-env-encrypted` did not. Fix: `encrypt` builds the sidecar from real `KEY=value` lines only, and the gate blocks a commented `KEY=plaintext`. **Both fixes were carried back to bikar (PR #189, `chore/dotenvx-isolate-and-comment-gate`, 2026-09-16) — the `dotenvx_isolated` helper + comment-stripping + gate cases 11/12; bikar's repo-specific comments preserved.** Blog write-up: `docs/issues/dotenvx-processenv-overlay.md`.
- **dotenvx v1→v2 breakage — FIXED 2026-09-16 (task #17; bikar #189 + blog omars-lab.github.io#227, both merged).** Both repos invoked the **unpinned** `npx -y @dotenvx/dotenvx`, which rolled over to **2.28.0**. Root cause is NOT that you "must call `dotenvx keypair`": v2 `encrypt` **mints the private key into the macOS login Keychain** (service `dotenvx`) and writes **no `.env.keys`**, and `decrypt` **falls back to that Keychain** when the file is absent — even with `-fk` at an empty file. So a fresh `encrypt` strands the only key copy in this machine's Keychain (invisible to `env-keys-push`, unavailable to the next machine) and `env-check`/`env-bootstrap` "succeed" off the Keychain with no `.env.keys` (the no-key guard stops guarding). `make test-env` failed 4 key-dependent assertions. **The lever is `--no-native`** ("disable OS secret store features" — documented only in `dotenvx keypair --help`, NOT in encrypt/decrypt help): with it, `encrypt` writes `.env.keys` again (v1 behavior, no Keychain touch) and `decrypt` reads the key only from file/env. **Fix = two lines in `env-sync.sh`: pin `@2.28.0` + pass `$NO_NATIVE` (`--no-native`) at every encrypt/decrypt call site.** Chosen over extracting the Keychain key via `dotenvx keypair` after each encrypt (manages a second key source) and over per-sandbox `HOME` isolation (unneeded once Keychain is out of the path) — tenet: a migration never buys a fork. No new test needed: env-sync.test.sh cases 6 + 9 already fail without it and pass with it; the pin makes it deterministic. `make test-env` → 44/44 green both repos. **Not a production regression:** real `.env.keys` comes from LastPass and both committed `.env.encrypted` are v2-shaped. Pivot records: bikar `docs/issues/2026-09-16-dotenvx-v2-keychain-key-storage.md`, blog `docs/issues/dotenvx-v2-keychain-key-storage.md`; `manage-secrets` skill Traps carries the operational note. **For any hand invocation of dotenvx encrypt/decrypt in these repos, pass `--no-native` or the key silently goes to the Keychain.**
- Repo secrets go to GitHub by piping `dotenvx get <NAME> -f .env` into `gh secret set` — values never displayed. supabase-js realtime needs Node ≥22 in workflows.
- Supabase project `gmwmrcmfywsdescglijg`: `bikar_patterns.folder text NULL` (NULL is the tree root) + UNIQUE `(user_email, name)`. Every studio save had failed `42P10` until that index existed — PostgREST rejects `ON CONFLICT` without a matching unique index, and the 201s were lies.
- `Prefer: resolution=merge-duplicates` overwrites only columns the body carries: the handler sends `folder: body.folder ?? null`, never an omitted key.
- The 42P10 class guard is `make supabase-check-upsert-keys` in coffee-house-sites (scans both repos' `on_conflict=` targets against live unique indexes; rejects partial/expression indexes; errors rather than narrows without a bikar checkout — which is why it is not a hook).

**Why:** each was a silent-success failure; "an acknowledgement is not an outcome" (bikar Tenet 31).

**How to apply:** never handle secret values in chat; verify a save against the DB, not the status code. Studio-side folder semantics: [[studio-folder-store]].
