**The X2D is physically on the LAN and reachable** (verified 2026-09-16 via `tools/bambu setup discover`, a passive receive-only SSDP listen on UDP 2021 — print-safe). Discovered identity:

- **host** `192.168.1.186` (iface wlan0) — goes in `.mcp.json` as `PRINTER_HOST`
- **serial** `20P6AJ641401412` — goes in `.mcp.json` as `BAMBU_SERIAL` (a device id, not a secret; the *access code/token* is the secret and is never committed)
- **firmware** `01.02.00.00`
- **model** First X2D [N6]

**The one remaining blocker (Omar's physical action):** the printer is **still CLOUD-bound**. The griches MCP transport (MQTT 8883 / FTPS 990) needs **LAN Mode + Developer Mode toggled ON at the printer's touchscreen** — this is the whole of what blocks task #8 live-hardware bring-up. `discover` reports `connect cloud ← still CLOUD-bound` until it is done. Nothing in software can flip it; it is a touchscreen toggle.

**The moment those toggles are on, the bring-up path is (all our CLI):**
1. Read the **access code** off the touchscreen (Developer Mode surfaces it). DONE 2026-09-16 — stored encrypted in the dotenvx `.env` as `BAMBU_TOKEN` (shape-validated: 8 chars, starts `c`, ends `9`), see [[secret-check-no-stdout-leak]].
2. Config is set: `.env` (dotenvx-encrypted) holds `BAMBU_TOKEN` + `PRINTER_HOST`/`BAMBU_SERIAL`/`BAMBU_MODEL=x2d`; `.env.keys` gitignored. Run the CLI under `dotenvx run -- bin/bambu …` so values reach `process.env`. (`setup mcp` writes a `.mcp.json` instead, but we use `.env`; **do NOT** create a root `.mcp.json` — Omar's constraint is no MCP registered with Claude Code.)
3. `tools/bambu setup doctor` — preflights every dependency + the LAN connection. GREEN 2026-09-16: MQTT TLS 8883 open (toggles confirmed working), config source=env, model=x2d.
4. `tools/bambu status show` — first read-only proof of transport (live temps/`gcode_state`). **DONE 2026-09-16 — #8 CLOSED.** Ran the first-party MQTT backend against the live X2D under `dotenvx run` and got a real report frame: `state: FINISH`, nozzle 34°C, bed 30°C, `progress 100% layer 179/179`, last job `Mini Twisted Dragon Egg - Only 12g` (the device's own cached last print — not one we dispatched; the "nothing ever printed" line in the plan is about *this project's* pipeline, the machine itself has prior jobs). Transport is proven end-to-end: connect mqtts:8883 (user `bblp`, token as password, `rejectUnauthorized:false`) → SUB report → PUB `pushing.pushall` → cached `print`/`mc_print` read back. The live frame uses the **standard Bambu field names** (`gcode_state`/`nozzle_temper`/`bed_temper`/`mc_percent`/`layer_num`/`total_layer_num`/`subtask_name`) — validates the `pick()` list in `status.ts renderStatus()` against real hardware, no X2D field-name drift. No competing MQTT client was open (checked via pgrep). Token never left the child env (summary output is temps/state only).

**Transport decision — D-055 (2026-09-16), amends D-054, PR #188 (merged).** Status reads now go over a **first-party MQTT backend we own** (`tools/bambu/src/backends/mqtt.ts`), NOT a spawned griches MCP. Why: `@griches/bambu-mcp` is not on npm (404) and ships no build, so the old `npx -y @griches/bambu-mcp` wiring never worked; the LAN status read is small and stable (subscribe `device/<serial>/report`, publish `pushing.pushall`, read cached `print`/`mc_print`), so we own it against the pinned `mqtt@5.14.1` lib. griches kept only as a **reference** for command shapes. Also fixed: `McpBackend` was leaking the whole `process.env` to the subprocess — now narrowed to PATH/HOME/proxy + the 4 printer vars.

**Dispatch went first-party too — #50, PR #243 (merged 2026-09-17, `f8b9ddb`).** Same reasoning as D-055: the griches MCP never ran, so `bambu print send` now owns both halves — **FTPS 990 implicit-TLS upload** (`tools/bambu/src/backends/ftps.ts` `FtpsBackend`, `basic-ftp@5.3.1` pinned; STOR to the FTP root under the bare basename; TLS session reuse left intact) + **MQTT `print.project_file`** (`MqttBackend.startProjectFile`, pure `buildProjectFileCommand`, references `ftp:///<name>`). Pause/resume/stop ride `buildPrintControlCommand`. `McpBackend` is out of the dispatch path (router keeps it only as the aspirational camera/ams fallback). Payloads grounded against pybambu/bambulabs_api/OpenBambuAPI; **three fields are a CAL-shaped bet for the dual-nozzle X2D** — `bed_type` (default `auto`), `ams_mapping` (default `[0]`), `md5` (default `""`) — exposed as `--bed-type`/`--ams-mapping`/`--md5` and to be settled by diffing `bambu print send --dry-run` against a **BambuStudio ground-truth MQTT capture** on the first real send (`docs/issues/first-party-dispatch.md`). `--dry-run` prints the exact FTPS target + MQTT payload without connecting — the review surface. Verification stops at the owner gate: FTPS handshake + physical publish are exercised only when Omar dispatches; `send` stays fail-closed (no `--yes` on Omar's behalf). This unblocks #9.

Then #9 (slice a real plate + first dispatch) stays owner-gated on a settled `CAL-*` bet — see [[owner-gated-and-on-hold]]. Printing itself is paused until a CAL bet settles; dispatch verbs default to confirm-before-send. CLI lives in `tools/bambu/` (run via `bin/bambu` or `npx tsx src/index.ts`; Node v22.22.3 pinned). ## The X2D-profile gap (Phase A discovery, growth) — DECIDED, not open

Two things about representing *this* machine surfaced during Phase A prep and are now recorded decisions, so they are not re-litigated:

- **bikar's machine menu does not ship the X2D.** `bikar:packages/knobs/src/machines.ts` `MACHINES` has 10 `PrintTarget` entries — Bambu side is only `bambu-x1c`/`bambu-p1s`/`bambu-a1`/`bambu-a1-mini`, all single-nozzle. No reading can be recorded honestly against "the X2D" until an X2D target exists (task #18/A1, own PR in bikar; build volume read off the device at bring-up, TODO-marked until then — the repo forbids invented numbers).
- **The `PrintTarget` schema has no nozzle concept at all:** `{ id, label, xMm, yMm, zMm, process: 'fdm'|'powder' }` — no nozzle-diameter field, no tool-count. **D-053** decided the X2D rides as a *single-nozzle-labelled FDM* target; the dual nozzle lives in the label + the record's profile header, **not** in a widened schema. Reversal condition: a knob that must branch on nozzle count earns the field (migration never buys a fork). PR #182.
- **The slice path is proven (A4/A5, 2026-09-16).** Bambu Studio **2.08.02.61** (a 2.8.x build) is installed at `/Applications/BambuStudio.app` and ships the **full X2D profile family** (machines `Bambu Lab X2D 0.2/0.4/0.6/0.8 nozzle`, 16 `@BBL X2D` process profiles, `@BBL X2D` filaments) — so the SKILL's "stable vs 2.8.x beta" question is settled empirically: this build has X2D. Headless slice works end-to-end: `bambu slice plate <coupon.stl> --settings "<machine>;<process>" --filament "<pla>"` → valid `.3mf` whose gcode reads `printer_model = Bambu Lab X2D`, `nozzle_diameter = 0.4,0.4` (dual nozzle confirmed in the profile, not the schema — validates D-053). The known-good Plate-1 trio (recorded in the bench sheet, PR #185): machine `Bambu Lab X2D 0.4 nozzle` · process `0.20mm Standard @BBL X2D` · filament `Bambu PLA Basic @BBL X2D 0.4 nozzle`. Headless binary: `/Applications/BambuStudio.app/Contents/MacOS/BambuStudio`. MC-4 fan pre-flight-eyeballed OK (full 360° revolve funnel, base on bed, flare up, supports off).
  - **CORRECTION (2026-09-16): `--load-settings`/`--load-filaments` take JSON *file paths*, NOT preset display names.** Passing the trio as bare names (`--settings "Bambu Lab X2D 0.4 nozzle;0.20mm Standard @BBL X2D"`) fails `operator(): can not find setting file`. The presets live as JSON in the app bundle: `/Applications/BambuStudio.app/Contents/Resources/profiles/BBL/{machine,process,filament}/<preset name>.json` (233 X2D-related JSONs). Working invocation is `--settings "<abs machine.json>;<abs process.json>" --filament "<abs filament.json>"`. **Fixed in PR #189**: `bambu slice` now resolves a bare preset name → that bundle JSON path (BBL vendor first), so the human-friendly names in the bench sheet work as written; a bad name fails with an actionable pre-slicer error. Same PR also set `+x` on `tools/bambu/bin/bambu` (shipped `100644`, so running the shim directly gave `Permission denied`) and added the regression guard `.claude/skills/bambu/scripts/slice-smoke.sh` (slices by name, asserts the X2D gcode header). Verified end-to-end 2026-09-16 on `build/stls/ClassicBrick.stl` (a simple LEGO brick) → `plate_1.gcode` reads `printer_model = Bambu Lab X2D`, `nozzle_diameter = 0.4,0.4`, 56 layers / 18,510 extrusion moves / 7m46s. **Smoke-run across the other LEGO sources 2026-09-16 (post-#189 merge):** `RosetteBrick.stl` and `StarBrick.stl` both slice clean by name (X2D header, `nozzle_diameter = 0.4,0.4`, 48 layer changes each) — the name→JSON resolver handles all three identically, no profile-specific surprise before Plate 2. Plate preview PNG for ClassicBrick pulled from the sliced 3mf (`Metadata/plate_1.png`, a clean 2×4 brick flat on the bed) and sent to Omar.
  - **Third gotcha (PR #190): the CLI router imports every backend at module load, `mqtt` among them (added with the #188 MQTT backend).** A `tools/bambu/node_modules` predating #188 fails deep in the router with an opaque `ERR_MODULE_NOT_FOUND` for `'mqtt'` — nothing points at `npm install`. After pulling #188/#189, run `npm --prefix tools/bambu install` (the main checkout's node_modules had only commander/tsx/typescript). `slice-smoke.sh` now preflights `node_modules/mqtt` and prints the exact install command before the Node stack trace.
  - **Second gotcha: `npm --prefix tools/bambu run bambu -- slice …` runs with cwd=`tools/bambu`**, so a relative STL path resolves against the wrong root (`no such file`). Pass the STL as an absolute path (or run via `bin/bambu` from the repo root).
- **AMS / filament schema CONFIRMED on the live X2D (2026-09-17, `bambu filament`, task #32, PR #192).** The read-only `pushing.pushall` frame exposes filament exactly where the H2-family docs said, resolving the research file's `[X2D-UNCONFIRMED — H2-proxy]` hedge (Topic 2): `print.ams.ams[]` (wrapper object, `ams_exist_bits`), each unit with `tray[]`; a **loaded** tray carries `tray_type`/`tray_sub_brands`/`tray_color` (RRGGBBAA)/`tray_info_idx` (e.g. `GFA00`)/`remain`, an **empty** tray reports only `{id,state}`. AMS 0 slot 0 read back real data (PLA Basic · #F5547C · GFA00 · 100%). **Divergence from the H2 docs:** the external spool is `print.vir_slot` **as an ARRAY** (id `254` sentinel + a loaded virtual slot id `255`), NOT the `print.vt_tray` object (absent on this machine) — so any parser must treat `vir_slot` as an array and must NOT treat an array as a record (`typeof [] === "object"` bit the first cut, dropping the loaded external slot; `isRecord()` in `filament.ts` now excludes arrays). This is the discovery seam #35's AskUserQuestion filament-pick reads.
- **The CLI backend is now grounded (D-054).** The griches-MCP-drives / BambuStudio-CLI-slices split was chosen inside #177 without a checked-in survey; A10/A11 fixed that — `docs/research/bambu-control-transport-survey.md` (16 options + AppleScript floor, an option rubric) and `docs/bambu-cli-design.md` (mermaid router, rubric verbatim, two-layer-split decision, X2D dual-nozzle validation gate). The shipped `router.ts` already matches the rubric-optimal shape; the design validates it rather than proposing a new one. PR #183. Landscape fact worth keeping: **no surveyed tool names the X2D** — best proxies name the H2 family (X2D's sibling, shares firmware `01.02.00.00`): griches (H2D-tested), DMontgomery40 (H2/H2S/H2D/H2C). So X2D dual-nozzle transport support is *unconfirmed everywhere* and is isolated to a bring-up validation gate, not assumed.
