# C2 assembly implementation survey — multi-part export, mating math, coupons

*Research date: 2026-07-28. Prepared as Appendix-A source material for the C2 design doc.*

Scope note: this survey deliberately does not re-cover ground in `research/code-cad-composition-survey.md` (BOSL2 attachment overview, build123d joints overview, OnShape/Fusion mate vocabularies, Manifold, Clipper2, Gridfinity, the Creative3DP fit ladder). It goes one layer down: exact encodings, exact transform compositions, slicer import behavior, coupon methodology, and pin engineering numbers. Claims from forums or vendor blogs are flagged as community/vendor-grade; primary specs and repository source code are preferred where they exist.

## 1. Multi-part export mechanics

**3MF encoding of "one file, N positioned parts" (primary source: core spec)**

- The [3MF core spec](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md) puts geometry in `<resources>` as `<object>` elements; an object contains either a `<mesh>` or `<components>`, never both. Object `type` values include `model` (must be manifold, consistent orientation, outward normals), `support`, `solidsupport`, `surface`, and `other` (not referenceable from the build).
- Transforms — on both `<component transform=...>` and `<build><item transform=...>` — are a 3D affine matrix serialized as **twelve space-delimited decimals in row-major order `"m00 m01 m02 m10 m11 m12 m20 m21 m22 m30 m31 m32"`**, with the fourth column implicit `[0,0,0,1]` (i.e., the last three values are the translation row). Same [spec](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md).
- The coordinate system is right-handed, z-up, origin at bottom-front-left; the `<model unit=...>` attribute defaults to `millimeter`. Transforms with negative determinant "MUST NOT change the sign of its volume" of the resultant shape — mirroring is constrained. Same [spec](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md).
- The assembled-positions guarantee bikar wants is spec-mandated for *components*: "a 3D manufacturing device MUST respect the relative positions of the component objects; it MUST NOT transform them relative to each other except as specified in the document," and for build items "a consumer MUST apply the transform prior to outputting the object" ([spec](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md)). This gives the C2 writer two encodings: N `<item>`s (slicers treat them as independent objects, free to re-arrange) vs one `<item>` wrapping a components-object (spec-locked relative positions). Note the tension: slicers observably re-arrange top-level items anyway (below), so "assembled" intent is safer expressed as one components-object.
- `<object partnumber=...>` is spec'd for toolchain tracking (preserve across edits, duplicate on split, remove on merge); `<object name=...>` is the human-readable label; `<item>` supports a `<metadatagroup>` of vendor `<metadata name=... preserve=...>` pairs — the hook for bikar's port/connect provenance. Same [spec](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md).

**Slicer import behavior (community/vendor-grade sources; the slicers do not formally document this)**

- **PrusaSlicer** distinguishes *objects* (each independently placed/arranged on the bed, each with its own settings) from *parts* of one object (keep relative positions). Importing a multi-object 3MF triggers a dialog asking whether to load "as multiple objects or as a single object with multiple parts" ([Prusa forum: Multipart objects in 3MF](https://forum.prusa3d.com/forum/prusaslicer/multipart-objects-in-3mf/), [Multiple objects in 3mf file](https://forum.prusa3d.com/forum/prusaslicer/multiple-objects-in-3mf-file/)). Loaded as objects, "each object has to obey the object rules and is placed on the bed" — assembled Z positions are lost unless at least one part touches the bed ([forum: position is lost when importing](https://forum.prusa3d.com/forum/prusaslicer/3mf-file-with-more-objects-position-is-lost-when-importing/)). Dragging several STLs in at once offers the same treat-as-one-multipart-object choice ([forum: load multiple 3mf](https://forum.prusa3d.com/forum/prusaslicer/load-multiple-3mf-like-i-did-with-stl/), [Prusa KB: Importing multi-material model](https://help.prusa3d.com/article/importing-multi-material-model_121191)). Per-object settings exist and are saved in the project 3MF ([Prusa KB: Per model settings](https://help.prusa3d.com/article/per-model-settings_1674), [Saving projects as 3MF](https://help.prusa3d.com/article/saving-projects-as-3mf_1773)); the CLI cannot answer the multipart dialog, a documented gap ([PrusaSlicer #11474](https://github.com/prusa3d/PrusaSlicer/issues/11474)).
- **Bambu Studio** auto-converts imported STEP into a multi-part object and generates an "Assembly View" that remembers assembled placements even after you split to objects for plating; adding parts later goes through the same "load as a single object with multiple parts?" dialog (select "No" to get individual objects) ([Bambu wiki: Assembly View Guide](https://wiki.bambulab.com/en/software/bambu-studio/assembly-view-guide)). Multi-part import keeps sub-objects "in their relative positions inside the model" ([Bambu forum](https://forum.bambulab.com/t/3mf-import-as-multiple-files-changes-origins/4334)); objects imported as separate objects get dropped to the bed, breaking pre-positioned Z ([Bambu forum: merge drops to bed](https://forum.bambulab.com/t/merge-items-bambu-studio-automatically-drops-to-bed/139831)). Re-importing a modified non-Bambu 3MF can reset per-object settings ([BambuStudio #3591](https://github.com/bambulab/BambuStudio/issues/3591)); multi-part/STEP workflow friction is an open issue ([#2724](https://github.com/bambulab/BambuStudio/issues/2724)).
- **Cura** has documented cases of changing/centring imported 3MF object positions ([Cura #18966](https://github.com/Ultimaker/Cura/issues/18966), [Ultimaker community: positioning data lost](https://community.ultimaker.com/topic/20500-cura-31-3mf-positioning-data-lost-on-import/)); the community workaround is select-all → "merge models," which restores relative positions **only if all parts were exported in the same world coordinate frame** ([Ultimaker community: origin and arrange](https://community.ultimaker.com/topic/44334-3mf-files-origin-and-arrange-all-models/)). Per-model settings are applied per selected model ([same thread](https://community.ultimaker.com/topic/44334-3mf-files-origin-and-arrange-all-models/)).

**Per-part export naming in code-CAD practice**

- OpenSCAD has no native multi-file export; the documented idiom is one module per part plus a mode variable driven from the command line: `openscad -Dmode=1 -o part1.stl params.scad`, usually wrapped in a Makefile ([OpenSCAD wiki: Multi-File export](https://github.com/openscad/openscad/wiki/Multi-File-export)); native support is a decade-old open request ([#1041](https://github.com/openscad/openscad/issues/1041), [#5785](https://github.com/openscad/openscad/issues/5785)). Third-party build systems impose the naming convention — e.g. scad-build emits `out/<scad_file>/<build_id>.stl` ([scad-build](https://github.com/unjordy/scad-build)). Dev snapshots with the `lazy-union` feature export each *top-level* statement as a separate 3MF object, but anything grouped in a module collapses to one object via the implicit union ([Bambu forum: OpenSCAD and 3MF](https://forum.bambulab.com/t/openscad-bambu-studio-and-3mf-files/96641), [OpenSCAD #5030](https://github.com/openscad/openscad/issues/5030)).
- CadQuery: `Assembly.toCompound()` + STL export produces one discontinuous-mesh STL; the community recommendation is to export one STL per solid and re-merge in the slicer; named multi-object 3MF export was an open feature request ([CadQuery #1345](https://github.com/CadQuery/cadquery/issues/1345), [#965](https://github.com/CadQuery/cadquery/issues/965), [import/export docs](https://cadquery.readthedocs.io/en/latest/importexport.html)).
- build123d: `export_stl()` is one-shape-per-file; the 3MF path (`Mesher.add_shape(..., part_number=...)`) is what carries part identity ([build123d import/export docs](https://build123d.readthedocs.io/en/latest/import_export.html)). STL itself carries no part name — names survive only via 3MF or filename, a recurring user complaint ([Bambu forum: keeping part names](https://forum.bambulab.com/t/workflow-for-keeping-part-names-upon-import-from-other-3d-programs/55033)).
- **Assembled world position vs own origin:** no surveyed tool documents a policy; observed practice splits by format. Slicers re-place objects on the bed anyway (Prusa/Bambu/Cura behavior above), so per-part STL position is nearly irrelevant *except* that the re-assembly workflows (Cura merge, Prusa/Bambu multipart import) all require parts exported **in a shared world frame**. Conclusion for bikar: STL = per-part, print-oriented, origin near bed; assembled placement belongs in the 3MF build/component transforms — matching design doc §6.

## 2. Frame mating math

**BOSL2 `attach()` (primary sources: wiki tutorial + reference)**

- The mating rule is documented as anti-alignment: "Imagine pointing the anchor arrows on the two objects directly at each other and pushing them together in the direction of the arrows until they touch" ([attach tutorial](https://github.com/BelfrySCAD/BOSL2/wiki/Tutorial-Attachment-Attach)). With `inside=true` the anchors point in the *same* direction instead (subtractive mating, same tutorial).
- In the two-anchor form, the mate wins over the child's own frame: "with parent-child anchor attachment the `anchor=` and `orient=` parameters to the child are ignored" ([attach tutorial](https://github.com/BelfrySCAD/BOSL2/wiki/Tutorial-Attachment-Attach)).
- `spin=` rotates "around the axis defined by the joined anchor vectors" — i.e., about the shared mate axis, exactly bikar's proposed spin-about-z — and is any scalar angle, not just multiples of 90° ([attach tutorial](https://github.com/BelfrySCAD/BOSL2/wiki/Tutorial-Attachment-Attach)). The reference explicitly warns it is *not* the child's `spin`: "The spin rotates around the attachment vector and is not the same as the spin argument to the child, which will usually rotate around some other direction that may be hard to predict" ([attachments.scad reference](https://github.com/BelfrySCAD/BOSL2/wiki/attachments.scad)). **The sign convention of `spin` is not explicitly documented** in either page — a gap bikar should not replicate.
- Because anti-aligning z leaves the rotation about z underdetermined, BOSL2 documents residual-orientation defaults: "When attaching to the TOP or BOTTOM: the FRONT of the child points to the front if possible; otherwise the TOP of the child points BACK. When attaching to other faces, if possible the child's UP anchor will point UP; otherwise, the BACK of the child points up" ([attach tutorial](https://github.com/BelfrySCAD/BOSL2/wiki/Tutorial-Attachment-Attach)); the reference states the side-face variant as "its FRONT is pointed DOWN and its BACK pointed UP" ([attachments.scad](https://github.com/BelfrySCAD/BOSL2/wiki/attachments.scad)). `overlap=` sinks the child in (negative gaps it out); `shiftout=` epsilon-extends for subtraction ([attach tutorial](https://github.com/BelfrySCAD/BOSL2/wiki/Tutorial-Attachment-Attach)).

**build123d `RigidJoint.connect_to()` (primary source: repository code, dev branch)**

- A joint's `joint_location` is given in **global** coordinates and immediately re-based onto the part: `self.relative_location = part_or_builder.location.inverse() * joint_location`; the world frame is recovered as `self.parent.location * self.relative_location` ([joints.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/joints.py)).
- Connecting moves the **other** part, one-shot: `Joint._connect_to` computes `relative_location = self.relative_to(other, **kwargs)` then `other.parent.locate(self.parent.location * relative_location)` ([shape_core.py, class Joint](https://github.com/gumyr/build123d/blob/dev/src/build123d/topology/shape_core.py)). The docs confirm it "only does a one time re-position of a part and does not bind them in any way" ([joints docs](https://build123d.readthedocs.io/en/latest/joints.html)).
- For rigid–rigid, the relative transform is `other_location = self.relative_location * other.relative_location.inverse()` ([joints.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/joints.py)) — which makes the two joint frames **exactly coincident** (z-aligned the *same* way, x-aligned too). There is **no anti-align flip and no spin parameter on rigid–rigid connects**: the author must bake the 180° flip and any rotational registration into one of the two `joint_location`s. This is the opposite convention from BOSL2 and the strongest argument for bikar making anti-alignment + explicit `spin` part of the `connect` verb rather than the port declaration.
- Where a spin-like knob exists, it is joint-typed: `RevoluteJoint.relative_to(other, angle=...)` returns `self.relative_axis.location * Rotation(0, 0, angle_degrees) * other.relative_location.inverse()` — rotation about the joint's local z — with a range check against `angular_range` and a documented workaround gotcha in the source: "Avoid strange rotations when angle is zero by using 360 instead" (`angle_degrees = 360.0 if angle_degrees == 0.0 else angle_degrees`) ([joints.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/joints.py)).
- Summary of the "exact convention" question: **BOSL2 = anti-aligned z at connect time + spin knob at connect time + documented (but incomplete) residual-orientation rules; build123d = coincident frames, all orientation authored into the joint declarations.** Neither documents a spin sign convention; BOSL2's own docs concede child-spin interaction is "hard to predict" ([attachments.scad](https://github.com/BelfrySCAD/BOSL2/wiki/attachments.scad)).

## 3. Contract validation precedents

- **build123d validates joint *kind*, not joint *dimensions*.** `RevoluteJoint.relative_to` raises `TypeError(f"other must of type RigidJoint not {type(other)}")`; `LinearJoint` accepts only `RigidJoint`/`RevoluteJoint`; `CylindricalJoint` and `BallJoint` only `RigidJoint`; out-of-range `angle`/`position` raises `ValueError` ([joints.py source](https://github.com/gumyr/build123d/blob/dev/src/build123d/joints.py)). Nothing anywhere in the joints module reads a diameter, depth, or clearance — kind compatibility and motion-range checks are the ceiling.
- **OnShape's check is solver-degrees-of-freedom, not contract.** The "mate over-defines the assembly" error fires when mates conflict or close loops; the guidance is community-level ("avoid having multiple mates constraining the same things… there is always some tolerance in computer math") ([Onshape forum #18037](https://forum.onshape.com/discussion/18037/mate-overdefines-the-assembly), [#27359](https://forum.onshape.com/discussion/27359/revolute-mate-overdefines-the-assembly)). No official help article documenting the error's semantics was found in this research (searches surfaced only forum threads — noted as an access/coverage limit).
- **FreeCAD splits both ways.** Assembly4 is explicitly solver-free — "Assembly4 was developed with the idea that a true constraint solver was not needed… parts are placed relative to each-other by matching features… No geometry is used to place and constrain parts" (LCS + ExpressionEngine) ([Assembly4 workbench docs mirror](https://reqrefusion.github.io/FreeCAD-Documentation-html/wiki/Assembly4_Workbench.html), [FreeCAD forum: "assembly without solver"](https://forum.freecad.org/viewtopic.php?style=5&p=283210)) — so it cannot flag inconsistency at all. FreeCAD 1.0's integrated assembly (Ondsel's contribution) uses a real solver with joint coordinate systems ([Ondsel blog](https://www.ondsel.com/blog/assembly-workbench-preview/)), and its failure modes are solver-shaped: miscounted DOF messages ([FreeCAD #27557](https://github.com/freecad/freecad/issues/27557)) and "solver goes unstable and blows up assembled parts" on inconsistent input ([FreeCAD #20377](https://github.com/FreeCAD/FreeCAD/issues/20377)) — a concrete argument for bikar's deterministic tree + tolerance-checked closure over any solve step.
- **No DSL found that errors on geometric mismatch of connectors.** Searches across build123d, OnShape, FreeCAD, and slicer-adjacent ecosystems surfaced no system that compares pin ⌀ + clearance against socket ⌀ at connect/compile time. The nearest relatives remain the ones the existing survey already cataloged (screws.scad tolerance classes, TolAnalyst stack-ups, Gridfinity's published 0.25 mm/side). Within the limits of this search, **bikar's connect-time contract check on general ports appears genuinely novel**, consistent with the narrowed claim in design doc Appendix B.1.

## 4. Fit/step-gauge coupon prior art

- **Maker's Muse Clearance & Tolerance Gauge** (the community reference coupon): print-in-place gauge testing clearances **0.15–0.5 mm** plus a 0.4 mm spinner; parts that free up tell you "what you need to use in your designs to create moving parts without them fusing together"; methodology is prescriptive — 0.15 mm layers, 3 perimeters, no supports/brim, good cooling ([makersmuse.com](https://www.makersmuse.com/clearance-and-tolerance-3d-printer-gauge), [Gumroad listing](https://makersmuse.gumroad.com/l/OxKwn)). Large families of similar labeled coupons exist on Printables, e.g. the [3DMakerNoob Clearance Tolerance Test](https://www.printables.com/model/116911-clearance-tolerance-test) and [numbered elephant-foot squares](https://www.printables.com/model/232635-numbered-small-squares-for-use-in-elephant-foot-co) (community-grade).
- **The closest analog to bikar's coupon-updates-profile loop is BOSL2's `$slop` calibration part**: print the test part, find the tightest labeled hole the plug fits, and "the number in front of that hole" *is* your printer's `$slop` — a coupon whose embossed labels map directly onto a language variable ([BOSL2 constants.scad wiki](https://github.com/BelfrySCAD/BOSL2/wiki/constants.scad); community remix: [Printables BOSL2 $slop test](https://www.printables.com/model/1251073-bosl2-slop-test)).
- **Bambu Studio documents a full coupon → setting methodology** (vendor-grade but detailed): separate settings for holes and contours — "XY Hole Compensation… only affects holes and does not change the outer size of the model; XY Contour Compensation… increases or decreases the overall XY size while keeping hole sizes unchanged"; calibrate each with its own model (metric-screw hole coupon for holes; a known reference object for contours), "print the model using the same Process profile and Filament you plan to use for your final part," iterate additively, and note "the hole diameter will increase by twice the compensation value" (the setting is per-side) ([Bambu wiki: XY Hole/Contour compensation](https://wiki.bambulab.com/en/software/bambu-studio/xy-hole-contour-compensation)). The same page's pre-flight checklist is a ready-made confound list for bikar's coupon docs: material shrinkage, elephant foot, moist filament, flow tuning, holes near nozzle size, missing chamfers/lead-ins, seam position.
- **PrusaSlicer, as of this research date, has *no* separate hole compensation** — only a single global "XY size compensation" (applies to interior and exterior perimeters alike; forum: "a crude tool which enlarges or reduces the XY dimensions… not selective" — [Prusa forum](https://forum.prusa3d.com/forum/prusaslicer/xy-size-compensation-units/)) plus first-layer-only [elephant foot compensation](https://help.prusa3d.com/article/elephant-foot-compensation_114487) (official KB; "values around 0.2 mm usually work well for the default 0.4 mm nozzle"). Splitting hole vs contour is a long-open request chain ([#1065 (2018)](https://github.com/prusa3d/PrusaSlicer/issues/1065), [#4561](https://github.com/prusa3d/PrusaSlicer/issues/4561), [#13815](https://github.com/prusa3d/PrusaSlicer/issues/13815), [#14953](https://github.com/prusa3d/PrusaSlicer/issues/14953)). SuperSlicer ships the split (hole size compensation incl. a vertical-hole variant) but with documented sign-direction confusion between the settings ([SuperSlicer discussion #3008](https://github.com/supermerill/SuperSlicer/discussions/3008), [#3505](https://github.com/supermerill/SuperSlicer/issues/3505)). Implication: bikar's printer profile cannot assume the slicer will fix holes — on PrusaSlicer the *compiler* must apply hole compensation to port geometry itself.
- Mapping measured coupon results onto settings, per the Bambu doc: measured diametral undersize ÷ 2 → per-side hole-compensation value; contour compensation calibrated separately against outer dimensions ([Bambu wiki](https://wiki.bambulab.com/en/software/bambu-studio/xy-hole-contour-compensation)). The one-variable-per-coupon discipline (separate hole and contour models, fixed filament/profile, iterate one setting) is explicit in the same doc; caliper measurement is assumed throughout ("Most require calipers to measure and correct"). No authoritative source recommending pin gauges specifically for FDM coupons was found — calipers are the documented norm (noting this as a coverage limit).

## 5. Printed pin/peg engineering

- **Minimum diameter — sources disagree.** [Hydra Research's design rules](https://www.hydraresearch3d.com/design-rules) give the tightest engineering rule: pin ⌀ "at least four times the extrusion line width to ensure at least two full perimeters are printed, a good rule of thumb is ø1.8 mm," plus mating clearances "~0.2 mm for loose fit and ~0.1 mm for tight fit." The [Hubs FDM design guide](https://www.hubs.com/knowledge-base/how-design-parts-fdm-3d-printing/) is far more conservative: "smaller diameter pins (less than 5 mm diameter) can be made up of only perimeter prints with no infill" (weak), recommends "the addition of a radius at the base of the pin" to kill the stress concentration, and for critical small pins says to drill a hole and "insert an off-the-shelf pin" instead. Mid-tier vendor guides commonly quote a 3 mm minimum with height ≈ 3× diameter (e.g., [Runsom](https://www.runsom.com/design-tips/fdm-design-guideline/), [FacFox](https://facfox.com/docs/kb/fdm-design-guideline)) — vendor-grade and not independently verified here. For bikar's ~⌀3 mm pins the honest reading: printable, but only a few perimeters thick — fit *and* strength must both be couponed.
- **Layer orientation strength — cited numbers.** CNC Kitchen's hook tests (vendor/community-grade but measured): PLA parts printed vertically (load across layers) failed at **55%** of the horizontally printed load; PETG at **46%**; ASA at **29%** ([CNC Kitchen: Comparing PLA, PETG & ASA](https://www.cnckitchen.com/blog/comparing-pla-petg-amp-asa-feat-prusament)). Peer-reviewed work on PLA/PETG confirms the pattern: in-plane (X/Y) properties are near-isotropic while Z-direction specimens show markedly lower strength and brittle failure from weak inter-layer adhesion ([Influence of layer orientation on mechanical properties of FDM PLA and PETG, ScienceDirect — abstract only, full text paywalled](https://www.sciencedirect.com/science/article/abs/pii/S2589152925002091)). Hubs states the general rule: "FDM components are inherently weaker in one direction due to layer orientation" ([Hubs](https://www.hubs.com/knowledge-base/how-design-parts-fdm-3d-printing/)). Consequence for C2: an upright-printed pin puts every layer boundary in shear/bending — pins should be printed lying down (or the coupon must test upright shear explicitly); no direct upright-pin shear dataset for PLA/PETG was found (unverified gap).
- **Chamfer/lead-in norms.** Verified numbers exist only for plate-edge chamfers: "include a 45° chamfer or radius on all edges of an FDM part touching the build plate" ([Hubs](https://www.hubs.com/knowledge-base/how-design-parts-fdm-3d-printing/)); "~0.3 mm chamfer to all the edges that will be in contact with the print surface" ([Hydra Research](https://www.hydraresearch3d.com/design-rules)). Missing "chamfers or lead-in features on holes" is listed as a dimensional-accuracy factor by [Bambu's wiki](https://wiki.bambulab.com/en/software/bambu-studio/xy-hole-contour-compensation). A specific lead-in chamfer size norm for pin tips (community folklore ~0.5–1 mm at 45°) could **not** be verified against any citable source — mark unverified; bikar should make it a knob with a couponed default.
- **Ecosystem printed connectors.** Multiboard's printed bolts are stated (vendor search result) to carry "a 0.25 mm tolerance" on every bolt, with lower-tolerance variants planned — the original page ([multiboard.io foundational update](https://www.multiboard.io/updates/foundational-update)) now redirects to their community site, so this is **unverified beyond the search snippet**. openGrid's printed snaps are documented first-hand: they "slide into the board's 28 mm grid holes," come in Full (6.8 mm boards) and Lite (3.4 mm) variants, and retain by flexure — the lock snap "expands outward, gripping the board tightly" via a coin-slot rotation; notably the guide publishes **no tolerance numbers at all** ([openGrid snaps guide](https://www.opengrid.world/guides/snaps/); cross-ecosystem snap models: [Printables](https://www.printables.com/model/1217876-opengrid-multiboard-snaps)). Pattern: ecosystems either publish one blanket tolerance (Multiboard, Gridfinity) or none — nobody parameterizes fit per printer profile the way bikar's §5 intends.

## 6. Assembly-level parameters (informs open question Q3)

- **OpenSCAD `$` special variables are the strongest "assembly overrides piece" precedent.** They are dynamically scoped: "Special variables pass along their value from within the scope from which the module or function is called. This means that special variables can potentially have a different value each time a module or function is called," vs regular variables which are "assigned at compile time" ([OpenSCAD manual, Other Language Features](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Other_Language_Features)). A caller (assembly) setting `$slop` transparently overrides every callee (piece) default — no plumbing. The failure mode is equally structural: any two libraries using the same `$name` collide silently along the whole call chain, which is why values can differ per call site.
- **BOSL2 wraps the raw variable in an accessor + default**: `$slop` is "the slop amount to make printed items fit closely. 0.0 by default," with the rule "if you write code that uses `$slop` be sure to reference it using `get_slop()`" (which supplies the default when unset), and per-call override is idiomatic — `threaded_nut(..., $slop=0.17)` ([BOSL2 constants.scad wiki](https://github.com/BelfrySCAD/BOSL2/wiki/constants.scad)). This is exactly a one-knob "material/printer profile" forwarded from any level of the assembly.
- **OnShape forwards parameters as explicit configuration inputs, not ambient state**: a Part Studio's configuration inputs "become options when inserting that Part Studio into an assembly"; assemblies can additionally define their own configurations, but those are "limited to configuring mates (not mate connectors), instances, and patterns" ([Onshape help: Part Studio and Assembly Configurations](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm), [Assembly Configurations](https://cad.onshape.com/help/Content/assembly_configurations.htm), [Insert parts and assemblies](https://cad.onshape.com/help/Content/Assembly/insert_parts_and_assemblies.htm)). The documented over-parameterization hazard: "every permutation of possible configuration inputs is one configuration" — the config space is the product of all inputs ([same help](https://cad.onshape.com/help/Content/PartStudio/part_studio_and_assembly_configurations.htm)); forwarding an assembly config *into* a part's config is a known awkward spot ([Onshape forum](https://forum.onshape.com/discussion/19846/passing-assembly-configuration-through-to-part-studio)).
- **CadQuery/build123d have no mechanism because Python is the mechanism** — parts are functions/objects, parameters are ordinary arguments ([build123d docs](https://build123d.readthedocs.io/en/latest/introductory_examples.html)); there is no precedent there for declarative override semantics.
- Net precedent for bikar's Q3: both working models (dynamic `$`-style knob with accessor+default; explicit config inputs at instantiation) support assembly-level override of piece defaults, and both deliberately keep the forwarded set *small and named* (one `$slop`; enumerated config inputs). No surveyed system does free-form "forward any piece param from the assembly," and OpenSCAD's collision hazard plus OnShape's permutation explosion are the documented reasons not to.

## Implications for the C2 design

1. **3MF writer (§1):** one `<object type="model" name="<Piece>" partnumber=...>` per piece; encode `export assembled` as a single components-object (spec-locked relative positions) *and/or* build items with 12-value row-major transforms; put port/connect provenance in `<item><metadatagroup>`. Validate matrices against the negative-determinant rule.
2. **`export parts` policy (§1):** per-piece STL, each in its **print orientation** at its own origin (z=0 on bed) — all three slicers drop/arrange objects anyway, and assembled placement is 3MF's job. Name as `<Assembly>-<Piece>.stl` (STL carries no internal name; the filename is the identity). Document the slicer "single object with multiple parts?" dialog in bikar's export docs.
3. **Spin semantics (§2, answers Q2):** adopt BOSL2's model — anti-aligned z at connect, `spin` as a connect-time scalar about the shared axis — not build123d's bake-orientation-into-the-port model (which forces authors to hand-compose flips). Unlike both prior systems, *document the spin sign convention and the residual-orientation default explicitly*, and write the closed-form composition (child_world = parent_world · parent_port · Flip180 · RotZ(spin) · child_port⁻¹) into the design doc with a worked sign test.
4. **Contract check (§3):** novelty stands — nearest precedents are build123d's joint-kind `TypeError`s and solver DOF errors. Mirror build123d's error ergonomics (typed, named, immediate) for kind mismatch; keep the closure check tolerance explicit and numeric, since FreeCAD's solver-blowup issues show what implicit loop reconciliation costs.
5. **Fit coupon (§4):** follow the BOSL2-$slop pattern — embossed labels that *are* profile values — and the Bambu discipline: separate hole-coupon and contour-coupon, one variable per coupon, same filament/profile as production, iterate additively; record diametral measurements and store per-side compensation = undersize/2. Since PrusaSlicer has no hole compensation, bikar's compiler must apply hole compensation itself rather than delegating to the slicer.
6. **Pins (§5):** treat ⌀3 mm as the floor (between Hydra's 1.8 mm and Hubs' 5 mm warning), default pins to lying-flat print orientation (Z-strength is ~half in PLA/PETG per CNC Kitchen), auto-fillet the pin base, and expose lead-in chamfer as a knob with a couponed (not literature) default.
7. **Assembly knobs (Q3, §6):** yes — but as a *small named set* (material profile, `$slop`-style fit scale, spin), with BOSL2-style accessor+default semantics ("assembly value overrides piece default; absent both, compiled default applies"). Reject free-form forwarding of arbitrary piece knobs; OpenSCAD's collision hazard and OnShape's configuration permutation explosion are the cautionary precedents.
