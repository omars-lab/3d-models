(`ggb_coords.py` dumps `coords.json` from the GeoGebra Apps API under Playwright;
`bikar points` dumps the naqsh side in mm; `naqsh_coords.py` divides the naqsh

polygons poly1 and pet by vertex ring (`7.4e-16`, `1.1e-14`). Largest residual
over the 23 rows: **9.9e-13**.

edges (a, b, c_{1}, d, e, f_{1}, h, j, i, k, ip, jp); 3 lists (`rosette`,

## 3. Oracle O3 — solid (preliminary, 2026-09-17; the comparator is P2.3b)

Reference: `make reference IN=export.ggb OUT=coords/coords.json UNIT=20 DEPTH=3`
in youtube-coords wrote `reference.scad` (42 `polygon()` + `linear_extrude(3)`
unioned, one per visible polygon in the Apps-API dump) and ran OpenSCAD 2021.01
to `reference.stl` (119 830 bytes). No bikar code touched it.

naqsh side: the smoke file plus `piece Coaster` / `extrude GimTvN9hw4U depth 3`,
rendered by `bikar render --piece Coaster --format stl --check`:

| naqsh file | triangles | volume (bikar) | mesh gate |
|---|---|---|---|
| correct | 380 | 17.7 cm³ | watertight, euler 2, bodies 1 — PASS |
| outer ring dropped | 92 | 2.1 cm³ | PASS |
| central rosette dropped | 380 | 17.7 cm³ | PASS — **byte-identical to the correct STL** |

The identical file is a property of `extrude`, not a bug: bikar's language
reference (`bikar-import` at `1bd5212`, `docs/language-reference.md` line 116)
says `extrude` "turns a 2D region (a pattern's bounded faces or a declared
`boundary`) into a watertight 3D solid". The central rosette's edges lie inside
the ring's bounded faces, so removing them changes no face union. O3 at the flat
stage therefore sees the silhouette only; interior ink is O2's claim.

IoU, Hausdorff, volume ratio and worst local deviation of these three pairs are
measured by `qiyas mesh compare` when it lands (P2.3b) and appended here.

## 5. What each oracle's inputs are

- O1 reads the engine's numbers, not the file's: `coords.json` is what the
  GeoGebra web app computed after `setBase64`, so a cached `<coords>` in the XML
  is never trusted over a recompute.
- O2 reads the loop's hero export and the view it was exported with; the
  naqsh render is placed on that grid from the same numbers, never aligned.
- O3 reads an OpenSCAD extrusion of the O1 dump's polygons; the only shared
  input with the naqsh side is the construction itself.
